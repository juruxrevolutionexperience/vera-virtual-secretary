Paso 1 Vera — Respuestas hardcodeadas & flujo Gmail 🔴 Urgente ›
Objetivo: Entender por qué Vera responde con texto fijo y por qué el calendario se crea automáticamente sin pasar por IA real.
Tareas0 / 7

  • Comparar variables de entorno (.env) entre tu máquina y la de tu compañero — especialmente las que apuntan al ai-service
  • Verificar que todos los servicios necesarios estén arrancados (ai-service, queue, Redis si aplica)
  • Revisar el prompt que recibe Vera: ¿llega a Claude/IA o va directo a una respuesta estática?
  • Inspeccionar logs del ai-service en tiempo real mientras se envía un correo de prueba
  • Localizar el código que genera el evento de calendario — ¿hay condición que lo dispara automáticamente?
  • Comparar versiones de dependencias del ai-service entre ambas máquinas
  • Documentar qué está fallando exactamente y en qué punto del flujo se rompe

⚡ Esto se hace con el proyecto abierto y logs a la vista. Comparte estructura de carpetas + .env (sin claves) cuando estés listo.

Paso 2 Auditoría BDD + ChromaDB 🟡 Importante ›
Objetivo: Verificar que la base de datos relacional y ChromaDB están bien estructuradas, se usan correctamente y escalan de forma segura.
Tareas0 / 9

  • Mapear qué se guarda en la BDD relacional: reuniones, correos, usuarios, tokens, etc.
  • Mapear qué se vectoriza y guarda en ChromaDB — ¿qué colecciones existen?
  • Verificar la relación entre ambas: ¿los IDs de ChromaDB se corresponden con registros de la BDD?
  • Comprobar si ChromaDB está realmente siendo consultado en el flujo de Vera
  • Revisar índices: ¿las consultas frecuentes tienen índices? ¿hay N+1 queries?
  • Evaluar crecimiento de datos: con 100 usuarios, ¿cuántas filas genera cada tabla por semana?
  • Revisar si hay soft delete o se borran datos de forma permanente
  • Verificar seguridad: datos sensibles cifrados, acceso por usuario aislado correctamente
  • Identificar mejoras: ¿qué se podría aprovechar más de ChromaDB que ahora mismo no se usa?

🗄️ Para esto necesitamos ver el schema de la BDD, las migraciones de Laravel y el código que escribe/lee de ChromaDB.

Paso 3 Security & Code Audit completo 🟣 Pre-producción ›
Objetivo: Dejar el proyecto listo para subir a servidor real — código, conexiones, dependencias y seguridad auditados.
Tareas0 / 10

  • Ejecutar composer audit — dependencias con CVEs conocidos
  • Ejecutar php artisan enlightn — auditoría completa de seguridad y performance
  • Verificar que .env no esté en el repositorio y que APP_DEBUG=false en producción
  • Revisar todas las rutas: ¿middleware de auth aplicado? ¿rate limiting en login y API?
  • Validación de inputs: ¿todos los Request tienen reglas? ¿hay queries crudas sin sanitizar?
  • Autenticación: contraseñas con bcrypt/argon2, tokens JWT firmados y con expiración
  • Revisar políticas y Gates de Laravel — cada usuario solo accede a sus propios datos
  • Claves API y secretos: ¿alguna hardcodeada en el código o accesible desde el frontend?
  • Revisar configuración de CORS, HTTPS y cabeceras de seguridad (CSP, X-Frame, etc.)
  • Checklist OWASP Top 10 — verificar que ninguna vulnerabilidad principal aplica al proyecto

🛡️ Este paso se hace después del Paso 2. Con la BDD ordenada, el audit tiene más valor real.

Paso 4 Auditoría & revisión de APIs nuevo 🔵 Pre-deploy ›
Objetivo: Verificar que todas las APIs del proyecto (internas, externas y de terceros) están bien implementadas, son seguras, eficientes y listas para producción.
Tareas0 / 11

  • Mapear todas las APIs externas usadas: Gmail, Google Calendar, Anthropic (Claude), ChromaDB — ¿cuáles están activas?
  • Verificar que todas las API keys están en .env y nunca expuestas en código o en el frontend
  • Revisar manejo de errores: ¿qué pasa si una API externa cae? ¿hay fallback o el sistema se rompe?
  • Revisar timeouts: ¿todas las llamadas a APIs externas tienen timeout definido?
  • Verificar rate limits de cada API externa — ¿podría el uso real superar los límites del plan actual?
  • Revisar la API interna de Laravel: ¿todos los endpoints están protegidos con auth? ¿responden correctamente los errores (401, 403, 404, 422)?
  • Comprobar que no hay endpoints que devuelvan más datos de los necesarios (over-fetching)
  • Verificar que el flujo OAuth de Gmail/Google Calendar renueva tokens correctamente cuando caducan
  • Revisar webhooks entrantes (si los hay): ¿se valida la firma/origen antes de procesarlos?
  • Comprobar que las llamadas a la API de Claude tienen el prompt correcto, temperatura adecuada y max_tokens controlado
  • Documentar todas las APIs usadas: endpoint, propósito, autenticación, límites — para tener un mapa claro antes de subir a producción

🔌 Este paso es clave antes de subir a servidor real. Una API mal gestionada en producción puede tumbar todo el sistema o exponer datos.
